# carelog — 개발 계획

육아 기록 앱. 수유 / 기저귀 / 수면을 빠르게 기록하고 오늘 요약을 본다.

## 개발 원칙: 기능별 세로 완성

화면을 전부 만든 뒤 DB를 붙이지 않는다. **기능 하나가 Today → SQLite → Records → 수정·삭제까지
전부 동작**하게 만든 뒤 다음 기능으로 넘어간다. 난이도 순서상 수유 → 기저귀 → 수면.

각 단계가 끝나면 변경사항 / 실행 방법 / 확인 항목을 보고하고 멈춘다.
사용자가 직접 실행해 확인한 뒤에만 다음 단계로 진행한다.

## 데이터 규칙

### 수유

| 필드 | 필수 | 비고 |
|---|---|---|
| 수유 시각 | 필수 | |
| 수유 종류 | 필수 | 모유 · 분유 |
| 모유 위치 | 조건부 필수 | 모유일 때만. 왼쪽 · 오른쪽 · 양쪽 |
| 수유량(ml) | 선택 | 분유일 때만. 입력하면 0보다 큰 정수 |
| 메모 | 선택 | |
| 생성·수정 시각 | 내부 | 사용자에게 노출하지 않음 |

**모유는 양이 없고 위치가 있다. 분유는 위치가 없고 양이 선택이다.** 자세한
설계와 마이그레이션은 5-5단계에 있다. `v4 → v5` 마이그레이션된 기존 기록만
`unspecified`로 보존하며, 새 기록은 이 상태로 저장되지 않는다.

**수유량을 입력하지 않으면 `0`이 아니라 `NULL`로 저장한다.**
`0ml`과 `양을 기록하지 않은 수유`는 다른 사실이다.

- 빈 입력 → `NULL`
- 값을 입력하는 경우 → **0보다 큰 정수만** 허용
- `0` 입력 → **입력 오류로 거부한다**

`0ml` 기록을 허용하면 그것이 `마지막 수유` 시각을 갱신해, 이 앱에서 가장 중요한
숫자를 오염시킨다. "물렸지만 먹지 않음"은 수유와 다른 종류의 이벤트이고 V1 밖이다.

집계 표시도 같은 원칙을 따른다. 오늘 분유량이 한 번도 입력되지 않았다면
`총량 0ml`로 보여주지 말고 항목을 숨기거나 `기록 없음`으로 표시한다.
합계는 분유만 더한다 — 모유는 양이 없고 `unspecified`의 양은 종류를 알 수 없다.

### 기저귀

종류(소변·대변·둘 다)는 필수다. 자유 문자열로 두면 오타가 조용히 저장되므로
DB 제약으로 세 값만 허용한다.

### 수면

수면은 시각이 아니라 **구간**이다.

- **종료 시각이 비어 있으면 "진행 중"이다.** 수유량 `NULL`과 같은 결로,
  "아직 안 끝남"과 "0분 잤음"은 다른 사실이다.
- **진행 중인 수면은 하나만 허용한다.** 앱에서 검사하고 DB 제약으로도 막는다.
- 종료 시각은 시작 시각보다 뒤여야 한다. 같은 시각도 허용하지 않는다.
- 1분 미만은 `0분`이 아니라 **`1분 미만`**으로 표시한다. 시작과 종료를 연달아
  누르면 실제로 생기는데, `0분`은 기록이 안 된 것처럼 읽힌다.
- 12시간 이상 진행 중이면 종료를 잊었을 가능성을 안내한다. 막거나 자동 종료하지는
  않는다 — 실제로 긴 수면도 있다.
- **겹치는 수면 기록은 저장을 허용하되, 합계에서는 구간을 병합해 중복 시간을
  한 번만 센다.** 낮잠 기록을 나중에 다듬다 보면 겹치는 일이 생기는데, 그때
  저장을 거부하면 더 성가시다. 병합하면 합계가 자연히 조회 구간 안에 들어가므로
  `24시간` 같은 상한을 숫자로 두지 않는다 — 서머타임에서 하루는 23시간이나
  25시간일 수 있다.

### 시각과 날짜 저장

| 값 | 타입 | 이유 |
|---|---|---|
| 수유 시각 (`occurred_at`) | epoch milliseconds `INTEGER` | |
| 수면 시작·종료 | epoch milliseconds `INTEGER` | |
| 생성·수정 시각 | epoch milliseconds `INTEGER` | |
| 아이 생년월일 | `YYYY-MM-DD` `TEXT` | 특정 순간이 아니라 달력상의 날짜다. epoch로 저장하면 시간대가 바뀔 때 날짜가 밀린다 |

SQLite는 ISO 8601 문자열도 정상 지원한다. epoch milliseconds를 고르는 이유는 그것이
옳아서가 아니라, 이 앱이 정렬·범위 검색·두 시각의 차이 계산을 많이 하고
JS와 왕복 변환이 없기 때문이다.

주의: SQLite의 `unixepoch` 계열 함수는 **초 단위**다. 밀리초 값을 그대로 넘기면 안 된다.
날짜 경계는 JavaScript에서 계산하고 숫자 범위로 조회한다.

```sql
WHERE occurred_at >= ? AND occurred_at < ?
```

`occurred_at`에는 인덱스를 건다. 모든 조회가 이 컬럼의 범위 검색이다.

### "오늘"의 경계

**기기 현지 시간 기준 00:00 이상, 다음 날 00:00 미만.**

새벽 수유를 전날 육아 주기에 포함하는 방식도 가능하지만 "하루 시작 시각 설정"이라는
새 기능이 필요해진다. V1에는 과하다.

끝 시각을 `시작 + 86,400,000ms`로 계산하지 않는다. 서머타임 지역에서는 하루가 항상
24시간이 아니다. 현지 달력으로 오늘 자정과 다음 날 자정을 각각 만든 뒤 epoch로 변환한다.
(한국은 서머타임이 없어 실제로 깨지지 않지만, 비용이 없으므로 처음부터 맞게 쓴다.)

### 경과 시간 갱신

"마지막 수유 1시간 24분 전"은 화면을 열어둔 동안 멈춰 있으면 안 된다.

- 화면 표시 중 1분마다 갱신한다
- 백그라운드에서 foreground로 돌아오면 즉시 갱신한다
- 화면을 벗어나면 타이머를 정리한다
- 갱신할 때마다 SQLite를 다시 조회하지 않는다. 마지막 수유 시각만 들고 현재 시각만 갱신한다

### 입력 검증

- **빈 문자열 판정과 숫자 변환을 분리한다.** `Number('')`는 `0`이므로
  `Number(input) || null` 같은 코드는 빈 입력과 진짜 `0` 입력을 둘 다 `null`로 만든다.
- 미래 시각은 저장하지 않는다. 허용하면 "마지막 수유 -5분 전"이 나온다.

### Today 화면 표시 예

```
마지막 수유      1시간 24분 전
오늘 수유        5회
오늘 분유량      220ml
```

### 4단계 — Today 요약과 통계 ✅

수유 횟수·수유량·기저귀 횟수·마지막 수유 경과 시간은 1~3단계에서 이미 붙었다.
**이번에 새로 만드는 것은 오늘 수면시간 하나와 카드 배치 정리다.**

#### 오늘 수면시간

**수면 전체 길이를 더하면 안 된다.** 날짜 경계와 겹치는 구간만 집계한다.
수면은 구간이라 하루에 걸치는 경우가 흔하다.

```
전날 23:00 → 오늘 06:00
  전날 통계  1시간
  오늘 통계  6시간
```

```
겹치는 구간 = max(0, min(종료 ?? now, 오늘 끝) - max(시작, 오늘 시작))
오늘 수면시간 = Σ 겹치는 구간
```

**계산은 `now`를 인자로 받는 순수 함수로 만든다.** 함수 안에서 `Date.now()`를
부르면 테스트가 실행 시각에 의존해, 진행 중 수면 케이스를 고정할 수 없다.

- **진행 중인 수면의 종료는 `오늘 끝`이 아니라 `현재 시각`이다.** 아직 오지 않은
  시간을 잤다고 셀 수는 없다.
- **합계는 화면에서 매분 다시 계산한다.** 조회 결과를 숫자 하나로 접어두면
  진행 중인 수면의 기여분이 얼어붙는다. 수면 행 목록을 들고 있다가 `now`로
  다시 더한다. 기존 1분 타이머를 쓰므로 DB를 매분 조회하지 않는다.
- **겹치는 수면이 하나도 없으면 `0시간`이 아니라 `기록 없음`이다.**
  수유량 규칙과 같다 — 안 잔 것과 기록하지 않은 것은 다르다.
  기록이 있는데 합계가 짧으면 `1분 미만`으로 구분해 쓴다.

진행 중인 수면은 정의상 항상 오늘과 겹치므로, 오늘 겹치는 수면 목록에서
종료가 비어 있는 행을 골라 쓰면 된다. 별도 조회가 필요 없다.

- [x] 자정을 넘긴 수면이 오늘 몫만 집계된다
- [x] 진행 중인 수면이 1분마다 반영된다
- [x] `calculateSleepDuration` 경계 8종 단위 테스트

#### 카드 배치

카드가 늘어 스크롤 경계에서 잘려 보인다. 2×2 그리드로 묶어 일반적인 기기에서
한 화면에 들어오게 한다. **`ScrollView`는 유지한다** — 작은 화면이나 큰 글꼴
설정에서는 여전히 넘친다.

#### 단위 테스트

구간 자르기는 지금까지 만든 것 중 경계 조건이 가장 많다. 이 순수 함수 하나만
테스트한다. 컴포넌트 테스트·스냅샷·커버리지 설정은 하지 않는다.

검사 대상: 하루 안에 들어오는 수면 / 전날 시작 / 다음 날 종료 / 하루 전체를
덮는 수면 / 진행 중 / 경계에서 안 겹침 / 여러 수면 합계.

테스트 파일은 `src/app` 밖에 둔다. 그곳은 라우터 루트라 파일이 그대로 라우트가 된다.

**Today 요약 카드까지가 V1이다. 별도 Statistics 화면은 V1.1.**

같은 숫자를 화면만 바꿔 다시 배치하는 것은 값을 하지 않는다. 별도 화면의 의미는
7일 추이·날짜별 비교·평균 수유 간격·일별 수면시간 그래프가 붙을 때 생기고, 그건 V1.1이다.
포트폴리오 관점은 README에 "SQLite 범위 조회와 순수 구간 계산으로 오늘 요약을
산출한다"고 쓰면 충족된다.

### 5단계 — 설정과 마감

#### 5-1. 설정 저장

아이 이름·생년월일, 앱 정보. 설정 탭이 새로 생긴다.

**생년월일은 이 프로젝트에서 처음으로 epoch가 아닌 값이다.** 달력 날짜라
`YYYY-MM-DD` `TEXT`로 저장한다. 기존 `todayRange`·`formatDay`는 전부 epoch
기준이므로 이 값에 그대로 쓰면 안 된다.

키-값 테이블이 아니라 **단일 행 테이블**에 이름과 생년월일을 각각의 컬럼으로
둔다. 타입과 의미가 스키마에 그대로 드러나기 때문이다. 여러 아이 확장과는
무관하다 — 그건 세 기록 테이블 전부에 `baby_id`가 붙어야 하는 별개의 작업이다.

정확한 DDL은 `src/db/migrations.ts`에만 둔다. 중복 문서화하면 코드와 갈라진다.

완료 기준: 이름·생년월일을 저장하고 앱을 재시작해도 남는다.
Today 상단에 아이 이름이 보인다.

**일령("생후 32일")은 넣지 않는다.** 출생 당일을 0일로 셀지 1일로 셀지
결정과 테스트가 따라붙는다. V1.1로 미룬다.

#### 5-2. 사용성 점검 — 코드 반영 완료

키보드 대응 / 접근성 라벨 / 큰 터치 영역 / 빈 화면 안내.

**키보드는 실기기에서 실제로 무엇을 가리는지 먼저 확인하고, 가리는 화면에만
대응한다.** Android에서 `KeyboardAvoidingView`는 `behavior`가 없으면 사실상
아무 일도 하지 않는다. 설정 화면에 들어 있는 것도 마찬가지다.

리뷰에서 나온 세부 항목:

- 아이 이름에 `maxLength={20}`, Today 인사문에 `numberOfLines={1}`.
  긴 이름이 `마지막 수유` 카드를 화면 밖으로 밀어낸다. 20은 시작값이고
  실기기에서 긴 이름을 넣어보고 조정한다. `numberOfLines={1}`은 기본
  `ellipsizeMode="tail"`이라 말줄임이 자동으로 붙는다.
- 설정 저장 연타 방지. 다만 같은 값 UPSERT라 데이터는 망가지지 않고 알림만
  겹친다 — 수면 종료 연타와 심각도가 다르다.
- 생년월일 버튼의 접근성 라벨에 **현재 값을 포함**한다. 라벨을 명시하면
  자식 `Text`의 날짜가 낭독에서 빠져, 라벨이 없느니만 못해진다.
  수유·기저귀·수면 폼의 날짜·시각 칩에는 라벨도 `accessibilityRole`도 없다.
  값은 자식 `Text`로 낭독되겠지만 버튼이라는 것과 조작 방법은 전달되지 않을
  수 있다.
- 로딩 중 비활성 상태가 눈에 보이는지 확인한다.
- Records 빈 화면에 다음에 무엇을 하면 되는지 안내한다.

완료 기준: 접근성 라벨·역할·선택 상태가 접근성 트리에 노출된다. 키보드를 띄운
상태에서도 입력과 저장·삭제 버튼에 접근할 수 있다. 빈 화면이 무엇을 하면 되는지
알려준다.

접근성 라벨·역할·선택 상태는 접근성 트리에서 확인됐고 주요 사용 흐름에도
영향을 주지 않으므로 유지한다. 화면 낭독기를 통한 자연스러운 낭독 검증은
V1 범위에서 제외한다.

라벨·잠금·빈 화면 안내는 반영했고 접근성 트리 덤프로 확인했다.
**키보드 가림은 확인하고 고쳤다.** 검증 기기에서 네 화면 모두 저장 버튼이
키보드 뒤에 있었고, 스크롤 영역이 줄지 않아 내려서 닿을 수도 없었다.
설정 화면의 `KeyboardAvoidingView`는 `behavior`가 `undefined`라 있으나 마나였다.

네 화면을 `KeyboardAvoidingView`로 감싸고 `behavior="padding"`을 준다. 그것만으로는
마지막 버튼의 스크롤 여유가 부족해 `contentContainerStyle`의 아래 여백을 48에서
120으로 올렸다. 키보드를 띄운 상태에서 저장·삭제 버튼에 닿는 것을 네 입력
화면에서 확인했다.

**접근성 라벨은 트리 덤프로 확인했다.** 라벨·역할·선택 상태가 실제로 붙어 있다.

새 설치에서 `user_version` 0 → 4가 도는 것은 확인했다. `run-as`로 DB를 꺼내
`PRAGMA user_version`이 4이고 네 테이블과 `idx_sleeps_one_active`를 포함한
인덱스 네 개가 있는 것까지 봤다. 5-4의 같은 항목은 이걸로 끝났다.

#### 5-3. 디자인 마감

카드·폼 스타일 중복을 **정말 합칠지 이 단계에서 판단한다.** 설정 폼까지
만들고 나서 보는 편이 정확하다. Today 카드가 스크롤 경계에서 잘려 보이는 것도
같이 본다.

**하단 고정 수면 버튼이 진행 상태에 따라 모습을 바꾼다.**

지금은 어두운 `수면 중` 카드와 주황 종료 버튼이 따로 떠서, 수면 중일 때만
카드 그리드가 통째로 밀린다. 새 요소를 추가하지 않고 하단 같은 자리의 버튼이
상태에 따라 모습을 바꾼다. 본문 카드 사이에 요소를 끼워 넣지는 않는다.

화면 전체를 덮는 오버레이나 `Modal`은 쓰지 않는다. 수면 중에도 수유·기저귀를
기록하고 기록 탭을 볼 수 있어야 한다. 수유·기저귀 버튼과 하단 탭은 그대로다.

**`app.json`의 `userInterfaceStyle`을 `"light"`로 고정할지 정한다.**
네이티브 설정이라 재빌드가 필요하지만, 5-4 뒤에 어차피 preview APK를 새로
만들므로 추가 비용은 없다.
지금은 `"automatic"`인데 JS 화면은 밝은 색을 하드코딩하고 `ThemeProvider`도
없다. 그래서 기기가 다크모드면 **날짜·시각 선택기만 어두운 배경으로 뜬다.**
수동 다크모드는 V1.1이므로 V1에서는 고정하는 편이 일관된다.

삭제 확인 Alert(UI 부수효과를 이름 뒤로 감춤)과 미래 시각 검사(비교 한 줄)는
추출 이득이 작아 **V1에서 공통화하지 않기로 이미 정했다.**

완료 기준: 합칠지 말지 정하고 이유를 이 문서에 남긴다.

**결정 — 하단 수면 컨트롤은 한 줄이고, 위 두 버튼과 높이가 같다.**

```
평상시    🛏 수면 시작
수면 중   🛏 수면 중 · 1시간 23분         수면 종료
```

여기서 알아야 할 것은 자는 중인지, 얼마나 됐는지, 어디를 눌러 끝내는지 셋뿐이다.
시작 시각은 기록 탭에 있으므로 넣지 않고, 12시간 초과는 버튼 배경색으로 알린다
(색은 낭독되지 않으므로 접근성 라벨에는 말로 넣는다).

- 두 상태가 `addButton`을 그대로 쓴다. 한 줄에 같은 글자 크기라 높이를 숫자로
  박지 않아도 같아진다. `height`로 고정하면 글자 크기를 키운 기기에서 잘린다.
  다만 `flexDirection: 'row'`를 주면 `alignItems`는 세로만 맡게 되므로
  가로 가운데는 `justifyContent: 'center'`로 따로 준다.
- 전체를 눌러 종료 확인창을 연다. 오터치해도 바로 종료되지 않도록 확인
  절차를 유지한다.
- **상태에 따라 버튼 색 전체가 바뀐다.** 평상시 `#3f3d56`, 수면 중 `#b85c00`,
  12시간 초과 `#9f3a20`. 아이콘과 글자만 바꾸면 눌렀는지 아닌지 알기 어렵다.
  12시간 안내를 노란 글씨로 얹던 방식은 주황 배경 위에서 대비가 나빠 버렸다.
  밝은 주황 `#ff9500`은 어두운 환경에서 지나치게 밝고, 흰 글자 대비가
  2.20:1로 큰 글자 기준(3:1)에도 못 미쳤다. 지금 두 색은 4.60:1과 6.77:1이다.
- **아이콘은 달이 아니라 침대다.** 신생아는 낮잠·밤잠을 가리지 않고 자므로
  달은 사실과 다르다. 낮잠·밤잠 구분은 V1 데이터에 넣지 않는다 —
  수면 구간 하나만 기록한다.
- 오른쪽 라벨은 `종료`가 아니라 `수면 종료`다.
- 본문의 별도 `수면 중` 카드는 제거한다. `오늘 수면` 요약 카드는 유지한다 —
  진행 중 시간과 오늘 누적은 다른 값이다.

**결정 — Records는 시각·색 점·종류·값을 한 줄에 둔다.**

```
14:18   ● 수면    1분 미만
14:13   ● 기저귀  소변+대변
          test memo
14:13   ● 수유    120ml
```

- **세 종류가 같은 형태다.** 왼쪽은 종류, 오른쪽은 그 종류의 값 — 수유는 양,
  수면은 잔 시간, 기저귀는 무엇을 쌌는지.
- 값은 있을 때만 그린다. 수유량 미입력이면 `양 기록 없음` 같은 문구도 넣지
  않는다. 값을 오른쪽 끝으로 밀지 않고 종류 옆에 붙인다.
- 메모만 있을 때 다음 줄에 작은 회색 한 줄로 둔다.
- **수면 종료 시각은 목록에 넣지 않는다.** 정확한 시작·종료는 줄을 눌러
  수정 화면에서 본다.
- 흰 카드와 둥근 종류 태그는 쓰지 않는다. 아이콘 대신 색 점을 쓴다 — 기저귀에
  어울리는 아이콘이 없어 셋을 맞추려면 하나는 억지가 된다.
- 날짜별 섹션과 줄 전체를 눌러 수정하는 동작은 그대로다.

수유 지속시간과 낮잠·밤잠 구분은 carelog에 없는 데이터이므로 참고한 앱에
있더라도 만들지 않는다. (좌우 모유 구분은 이후 5-5단계에서 V1 범위로 들였다.)

**결정 — 카드·폼 스타일은 합치지 않는다.**
세 폼은 겹쳐 보이지만 실제로 다르다. 수유는 수유량, 기저귀는 종류 칩,
수면은 시각이 두 개다. 겹치는 로직은 이미 `mergePickedDateTime`과 `time.ts`로
빠져 있고, 남은 것은 스타일 상수뿐이다. 공통 모듈을 만들어도 각 폼이 다시
덮어쓰게 되어 파일만 하나 늘어난다.

**결정 — `userInterfaceStyle`을 `"light"`로 고정한다.**
JS 화면이 밝은 색을 하드코딩하고 `ThemeProvider`가 없어, 기기가 다크모드면
날짜·시각 선택기만 어둡게 떴다. 네이티브 설정이라 지금 개발 빌드에는
반영되지 않는다. 5-4의 preview APK에서 다크모드 기기로 확인한다.

**Today 화면은 세로 여유가 거의 없어, 무엇이든 한 줄 늘면 카드가 잘린다.**
하단 수면 컨트롤을 한 줄로 두어 원인 하나를 없앴고, 나머지 둘을 같이 처리했다.

- `오늘 수면` 값이 두 줄로 접히면서 그 카드가 잘렸다. 반 폭 카드에 32pt로는
  `16시간 20분`이 한 줄에 들어가지 않는다. 신생아가 하루 14~17시간을 자니
  테스트 데이터만의 문제가 아니라 실사용 첫날 나오는 값이다.
  하루 합계에는 `formatDurationCompact`를 쓴다 — 1시간이 넘으면 분을 버리고,
  버린 분이 있으면 `16시간+`처럼 `+`를 붙인다. 반올림이 아니라 버림이라
  `약 16시간`은 위로 오해하게 만든다. 개별 수면의 분은 기록 탭에 그대로 남는다.
- 값이 접히면 카드가 높아지므로 `cardValue`에 `numberOfLines={1}`을 박고,
  카드 여백을 20에서 16으로 줄여 여유를 뒀다. `cardsContent`의
  `paddingBottom`도 4에서 12로 올렸다.

### 5-5단계 — 수유 종류 분리 (모유·분유) ✅

**지금 `수유량`은 두 가지 다른 사실을 같은 `NULL`로 저장한다.**

```
모유를 먹였다        → 양을 알 수 없다      amount_ml NULL
분유인데 안 적었다    → 양을 기록 안 했다     amount_ml NULL
```

둘은 다른 사실인데 구분이 안 된다. 모유가 섞이면 `입력된 수유량`이 하루 섭취량
근처도 아닌 숫자가 되고, "양을 적어야 하나?"라는 질문이 매번 생긴다.

#### 데이터

`feedings`에 두 열을 더한다. 마이그레이션 `4 → 5`.

```
kind  TEXT NOT NULL   'breast' | 'formula' | 'unspecified'
side  TEXT            'left' | 'right' | 'both'   모유일 때만
```

- **모유는 양이 없고 위치가 필수다. 분유는 위치가 없고 양을 선택적으로
  기록한다.** 서로의 열은
  `NULL`이어야 한다. `CHECK`로 강제한다 — 앱에서만 막으면 언젠가 어긋난다.
  - `kind = 'breast'` → `amount_ml IS NULL AND side IS NOT NULL`
  - `kind = 'formula'` → `side IS NULL`
  - `kind = 'unspecified'` → `side IS NULL` (기존 기록 전용, 새로 만들지 않는다)
- **`side`는 자유 문자열로 두지 않는다.** 기저귀 `kind`와 같은 이유로 세 값만
  `CHECK`로 허용한다.
- `amount_ml`의 기존 규칙(`NULL` 허용, 값이 있으면 0보다 큰 정수)은 그대로다.
  분유인데 양을 모를 수도 있다.
- **테이블을 다시 만드는 김에 정수 제약을 실제로 건다.** 지금 `CHECK`는
  `amount_ml > 0`뿐이라 `1.5`가 통과한다. SQLite의 `INTEGER`는 선언만으로
  정수를 강제하지 않는다.

  ```sql
  CHECK (
    amount_ml IS NULL OR
    (typeof(amount_ml) = 'integer' AND amount_ml > 0)
  )
  ```

  지금은 입력이 `keyboardType="number-pad"`라 소수점을 칠 수 없어 실제 노출은
  좁다. 그래도 규칙이 "0보다 큰 정수"라고 선언돼 있으면 DB가 그걸 강제해야 하고,
  나중에 가져오기 같은 경로가 생기면 폼을 우회한다.
- SQLite는 `ADD COLUMN`으로 이런 교차 `CHECK`를 붙이기 어렵다. 새 테이블을
  만들고 복사한 뒤 이름을 바꾸는 표준 절차로 간다. `sleeps`처럼 부분 유니크
  인덱스가 걸린 테이블이 아니라 옮길 인덱스는 `idx_feedings_occurred_at` 하나다.

**분유의 `amount_ml`은 선택이다.** 새벽에 급히 적는 앱에서 양을 강제하면 모르는
사람은 추측해서 적는다. 틀린 숫자가 빈칸보다 낫지 않다. 원래 문제였던 모호함은
이미 사라진다 — `kind = 'formula' AND amount_ml IS NULL`은 "분유인데 양을 기록하지
않음"으로 명확하다. 값이 있을 때만 양수 제약이 걸린다.

**기존 행은 `unspecified`로 보존한다.**

```
kind        unspecified
side        NULL
amount_ml   기존 값 그대로
```

`formula`로 옮기는 것은 추정이다. `amount_ml`이 `NULL`인 행은 모유일 수도 있고
양을 적지 않은 분유일 수도 있다. 양이 있는 행조차 유축한 모유였을 가능성을
지금 스키마만으로는 배제할 수 없다.

`unspecified`는 마이그레이션된 기존 기록에만 쓴다. **입력 화면에는 모유·분유
둘만 보여주고 새 기록은 이 상태로 저장되지 않는다.**

구현 전에 v4 기준 데이터를 준비했다 — 수유량 `NULL` 1건과 `120ml` 1건, 두 행의
`id`·`occurred_at`·`amount_ml`·`note`·`created_at`·`updated_at`을 기록해 뒀고
DB 사본도 보관했다. 마이그레이션 후 이 값들을 그대로 대조한다.

#### 입력 화면

기저귀의 종류 칩과 같은 구조를 쓴다. 이미 `accessibilityRole="radio"`와
선택 상태가 붙어 있어 그대로 따라 하면 된다.

```
수유 종류   [ 모유 ] [ 분유 ]

모유 선택 시   위치   [ 왼쪽 ] [ 오른쪽 ] [ 양쪽 ]
분유 선택 시   수유량  [        ] ml
```

- **종류를 바꾸면 반대쪽 입력값을 버린다.** 모유로 바꿨는데 아까 적은 `120`이
  남아 있으면 `CHECK`에 걸리거나 조용히 잘못 저장된다.
- 수정 화면에서도 같다. 기존 기록의 종류를 바꾸면 반대쪽 열을 `NULL`로 쓴다.
- **`unspecified` 기록을 열면 모유·분유 어느 쪽도 선택되지 않은 상태로 둔다.**
  `기존 기록이라 수유 종류가 지정되지 않았습니다` 정도로 알린다.
  종류를 고르지 않아도 시각과 메모는 수정할 수 있고 `unspecified`가 유지된다.
  모유나 분유를 고르면 그때 전환된다.
- **새 기록은 종류를 반드시 고르게 한다.** 새로 `unspecified`가 만들어지면
  마이그레이션 전용 상태가 다시 생겨나 영원히 남는다.

  **이건 `CHECK`로 막을 수 없다.** DB는 기존 행 때문에 `unspecified`를 허용해야
  하고, INSERT가 새 기록인지 마이그레이션된 행인지 구분하지 못한다. DB API의
  타입 경계에서 막는다.

  ```ts
  type FeedingBaseInput = {
    occurredAt: number;
    note: string | null;
  };

  type NewFeedingInput = FeedingBaseInput &
    (
      | { kind: 'breast'; side: BreastSide; amountMl: null }
      | { kind: 'formula'; side: null; amountMl: number | null }
    );

  // 수정 경로만 unspecified를 받는다.
  type StoredFeedingInput =
    | NewFeedingInput
    | (FeedingBaseInput & {
        kind: 'unspecified';
        side: null;
        amountMl: number | null;
      });
  ```

  판별 유니온으로 두면 `unspecified`뿐 아니라 **모유 + 수유량, 분유 + 위치
  조합까지 컴파일 단계에서 막힌다.** DB `CHECK`는 최종 안전장치로 남는다.
  `insertFeeding`은 이 타입만 받고, `unspecified` 유지는 수정 경로에서만
  가능하다.
- **기본 선택은 두지 않는다.** 마지막에 저장한 종류를 기본값으로 쓰면 입력
  화면이 DB를 읽어야 하는데, 그건 좌우 자동 추천을 V1.1로 미룬 이유와 같다.
  먼저 매번 고르게 하고, 실제로 탭 하나가 불편한지 보고 나서 넣는다.

#### Today 화면

**`입력된 수유량` 카드의 의미가 바뀐다.** 모유가 섞이면 이 숫자는 하루 섭취량이
아니라 분유 합계다. 이름을 `오늘 분유량`으로 바꾼다.

```
오늘 수유    5회        ← 모유·분유 합계, 그대로
오늘 분유량  360ml      ← 분유만. 분유가 없으면 `기록 없음`
```

모유 횟수를 따로 세는 카드는 만들지 않는다. 카드가 넷에서 다섯으로 늘면 세로
여유가 없는 화면이 또 잘린다. 종류별 횟수는 기록 탭에서 보인다.

`마지막 수유` 카드는 경과 시간만 그대로 둔다. 화면 세로 여유가 이미 빠듯하고,
종류는 기록 탭에서 확인할 수 있다.

#### 기록 화면

한 줄 구조는 그대로 두고 값만 바꾼다.

```
18:31   ● 수유    분유 120ml
16:28   ● 수유    모유 왼쪽
15:59   ● 수유    분유            ← 분유인데 양을 안 적음
13:02   ● 수유    기존 기록 · 120ml   ← 기존 기록, 양이 있던 경우
11:40   ● 수유    기존 기록          ← 기존 기록, 양이 없던 경우
14:13   ● 기저귀  소변+대변
14:08   ● 수면    1분 미만
```

새 기록은 항상 모유·분유 세부 값이 붙는다. **기존 `unspecified` 기록은 양이
있든 없든 `기존 기록`을 먼저 붙인다.** 양만 `120ml`로 보여주면 분유 기록으로
오해한다 — 추정하지 않으려고 `unspecified`를 뒀는데 화면에서 감추면 의미가
없어진다. 양이 없으면 빈칸 대신 `기존 기록`만 남는다.

**`src/db/timeline.ts`도 함께 고친다.** Records는 `feedings`를 직접 읽지 않고
통합 타임라인을 거친다. `TimelineEntry`에 `feeding_kind`·`feeding_side`를 넣고
`UNION ALL`의 수유 절에서 두 열을 뽑아야 한다. 다른 두 절은 `NULL`로 자리를
맞춘다 — 기저귀의 `diaper_kind`, 수면의 `sleep_ended_at`과 같은 방식이다.

**종류 열은 `수유`로 두고 모유·분유는 값 열에 넣는다.** 종류 열에 `모유`/`분유`를
직접 쓰는 안도 있으나, 기저귀에서 `소변+대변`을 종류 열에서 값 열로 옮겨 세 줄
구조를 통일한 결정과 어긋난다. 수유만 종류 열이 둘로 쪼개진다. 바꾸려면 기저귀도
같이 바꿔야 한다.

#### 하지 않는 것

- **유축은 넣지 않는다.** 모유·분유 둘로 끝낸다. 유축을 넣으면 "유축한 모유를
  먹인 것"과 "짜기만 한 것"이 갈라지고, 후자는 수유가 아니라 별개의 기록이다.
- **수유 지속 시간, 좌우 자동 추천(`다음은 오른쪽`)은 V1.1로 미룬다.** 지속
  시간은 시작·종료가 필요해 수면과 같은 구간 모델이 되고, 자동 추천은 마지막
  모유 기록을 읽어야 해서 입력 화면이 DB에 의존하게 된다.

#### V1에 넣는다

마이그레이션과 세 화면이 모두 바뀌므로 작은 작업은 아니다. 그래도 출시 전이
훨씬 싸다 — 출시 후에도 기존 기록은 `unspecified`로 보존할 수 있지만, 미지정
기록이 쌓이기 전에 모델과 입력 흐름을 확정하는 편이 단순하다.

#### 결과 — 전부 통과했다

빈 DB에서 `0 → 5`가 돌아 네 테이블과 네 인덱스가 만들어졌다. v4 기준 데이터
2건(수유량 `NULL` 1건, `120ml` 1건)이 있는 DB에서 `4 → 5`를 돌려 여섯 컬럼과
`idx_feedings_occurred_at`이 그대로 보존되는 것을 확인했다. 두 행 모두
`unspecified` + `side NULL`이다.

CHECK 13가지를 전수로 넣어봤다. `kind`·`side` 임의 문자열, 모유 + 위치 `NULL`,
모유 + 수유량, 분유 + 위치, 미지정 + 위치, 수유량 `1.5`·`0`·음수는 거부하고,
모유 + 위치, 분유 + 수유량, 분유 + 수유량 `NULL`, 미지정 + 기존 수유량은
허용한다. `typeof` 검사를 넣기 전이었다면 `1.5`가 통과했을 값이다.

화면에서는 새 모유가 위치 없이 저장되지 않고, 새 분유는 양 없이 저장된다.
종류를 바꾸면 반대쪽 입력이 버려진다. 기존 `unspecified` 기록은 종류를 고르지
않고 저장해도 유지되며 `created_at`도 밀리지 않는다. 모유 위치 수정, 분유
수유량 수정, 삭제도 확인했다.

집계는 `unspecified 120ml`이 있는 상태에서 분유 `150ml`을 저장해 확인했다 —
`오늘 수유`는 3회지만 `오늘 분유량`은 `270ml`이 아니라 `150ml`이다.

`unspecified` 행은 앱에서 만들 수 없고 마이그레이션으로만 생기므로, 이 검증을
다시 하려면 v4 상태의 DB 사본이 필요하다.

#### 완료 기준

마이그레이션

- 빈 DB에서 `0 → 5`가 한 번에 돈다.
- 기존 데이터가 있는 DB에서 `4 → 5`가 돈다.
- 테이블을 다시 만드는 과정에서 `id`, `occurred_at`, `amount_ml`, `note`,
  `created_at`, `updated_at`이 모두 그대로 보존된다. 수유량이 `NULL`인 행과
  양수인 행을 모두 확인한다.
- `idx_feedings_occurred_at`이 새 테이블에 다시 만들어진다. 인덱스는 테이블과
  함께 사라지므로 재생성을 빠뜨리기 쉽다.

제약

- `kind`는 `breast`·`formula`·`unspecified` 세 값만 허용한다.
- `side`는 `NULL`이거나 `left`·`right`·`both` 중 하나다. `NULL`도 정상값이다 —
  분유와 기존 기록은 반드시 `NULL`이어야 한다.
- `breast`는 `side`가 반드시 세 값 중 하나여야 한다. `breast` + `side NULL`을
  거부한다.
- 모유 + 수유량, 분유 + 위치 같은 잘못된 조합을 거부한다.
- `side`에 임의 문자열을 넣으면 거부한다.
- `amount_ml`은 `NULL`과 양의 정수만 허용한다. `1.5`, `0`, 음수는 거부한다.
- 새 기록에서는 `unspecified`가 생기지 않는다 — DB가 아니라 `insertFeeding`의
  타입이 막는다.

화면

- 모유·분유를 각각 저장하고 수정할 수 있다.
- `unspecified` 기록을 열면 종류가 미선택이고, 안 고르고 저장해도 유지된다.
- `오늘 분유량`이 분유만 합산한다. 모유와 기존 기록의 양은 빠진다.

#### 개인정보 처리방침

**데이터를 수집하지 않아도 필수다.** Play 정책은 개인·민감정보에 접근하지 않는
앱도 처리방침을 제출하도록 요구하고, **Play Console의 URL 칸과 앱 안쪽 양쪽에**
링크나 본문이 있어야 한다. 앱 쪽은 설정 화면 `앱 정보` 아래 링크 한 줄이면
되지만 **코드 변경이라 Play용 빌드 전에 넣어야 한다.**

내용은 짧지만 문구를 정확히 써야 한다.

- **`수집하는 개인정보 없음`이라고 쓰지 않는다.** 앱은 아이 이름·생년월일과
  수유·기저귀·수면 기록을 입력받아 저장한다.

  > 앱은 아이 정보와 육아 기록을 입력받아 기기에서 처리·저장한다. 개발자는
  > 이를 자체 서버로 전송받거나 제3자에게 공유하지 않는다.

  **`수집`이라는 말을 처리방침과 데이터 보안 양식에서 같은 뜻으로 쓰지 않는다.**
  Play 양식에서 `수집`은 원칙적으로 기기 밖으로 전송하는 것을 뜻하고, 기기
  안에서만 처리되는 데이터는 수집으로 신고하지 않는다. 처리방침 문구를 그대로
  양식에 옮기면 잘못 신고하게 된다.
- **삭제 설명에서 자동 백업을 분리한다.**

  > 기기 내 데이터는 앱 데이터 삭제나 앱 제거로 지울 수 있다. 데이터는 Android
  > 자동 백업 대상이 될 수 있으며, 생성된 백업은 사용자의 Google 백업 설정에서
  > 관리되고 개발자는 접근하거나 직접 삭제할 수 없다.

  백업은 확정이 아니라 가능성이다. `allowBackup: true`여도 사용자 설정·네트워크·
  주기에 따라 백업되지 않을 수 있다. 반대로 앱을 지우면 모든 사본이 사라진다고
  약속해서도 안 된다.
- 그 밖에 들어가야 할 항목: 앱 이름 `안녕아가`, Play 등록 개발자명, 문의 이메일,
  처리 목적, 보유 기간, 삭제 방법, 보안 처리 방식, 시행일과 수정일.
  광고·분석 SDK가 없다는 사실도 적는다.

않는 웹페이지를 요구하며 PDF는 허용하지 않는다. 저장소의 `PRIVACY.md`를 원본으로

스크린샷은 화면이 확정된 뒤에 찍었다. 먼저 찍었다면 수면 컨트롤과 수유 종류
분리 때 다시 찍어야 했다.

출시 전에는 "Google Play 출시까지 진행"이라고 쓸 수 없다. 실제 출시 후에 넣는다.

`web` 스크립트는 제거했다. `expo-sqlite`의 Web 지원은 `metro.config.js`의 wasm
설정과 `Cross-Origin-*` 헤더가 필요한 alpha 기능인데 V1은 Android 전용이다.
남은 `react-dom`·`react-native-web` 의존성은 이 단계에서 함께 정리한다.

**결정 — V1은 자동 백업을 허용한다.** `app.json`에 `android.allowBackup: true`를
명시했다. 기본값과 같지만 기본값에 기대지 않는다.

앱 자체에는 내보내기나 동기화 기능이 없다. 자동 백업이나 기기 간 전송이
동작하지 않는 환경에서는 기기 변경·분실 시 기록을 복구할 수 없으므로,
V1은 자동 백업을 허용한다.

과장하지 않는다. `true`는 "기기를 바꾸면 반드시 복구된다"가 아니라 **자동 백업
대상이 될 수 있다**는 뜻이고, 사용자 백업 설정·네트워크·주기에 따라 백업되지
않을 수 있다. 반대로 `false`도 "절대 기기 밖으로 안 나간다"를 보장하지 않는다 —
클라우드 백업을 막아도 기기 간 전송은 남을 수 있다.

그래서 설정 화면도 `기기에만 저장됩니다`가 아니라 `로그인 없이 사용할 수
있습니다`로 쓴다. 개인정보 처리방침 문구도 이 결정에 맞춘다.

**표시 이름은 `안녕아가`로 정했다.**

```
홈 화면 · app.json name    안녕아가
Play 제목                  안녕아가 - 수유·기저귀·수면 기록      19자
저장소 · slug · 패키지      carelog / com.kjw1801.carelog 유지
```

기능을 그대로 옮긴 이름은 이미 다 쓰이고 있었다. Play 검색에서 `CareLog`,
`Baby Care Log`, `BabyCareLog`는 같은 이름의 앱이 여럿 나왔고, `베이비` 계열은
`베이비타임`·`베이비케어`·`베베로그` 사이에 끼는 자리였다.

`안녕아가`는 예비 검색에서 같은 이름의 육아 기록 앱이 발견되지 않았다.
동일 상호의 애견업체는 있으나 업종이 다르다.

`app.json`의 `name`(홈 화면에 뜨는 앱 이름)과 스토어 등록명은 다른 값이고,
전자는 바꾸면 네이티브 재빌드가 필요하다. `slug`와 `extra.eas.projectId`는
기존 Expo 프로젝트 및 빌드 이력을 유지하기 위해 변경하지 않는다.

상표 등록은 출시 조건이 아니다. 개인 포트폴리오 앱 규모에서는 예방 점검
정도로 두고, 앱이 실제로 자리를 잡거나 유료화·법인화할 때 `안녕아가` 출원을
검토한다. Play의 사칭 정책은 이름이 겹치는지가 아니라 사용자가 기존 업체와
관계있다고 오인할 정도인지를 본다. 기존 업체와의 관계를 암시하지 않고,
독자적인 로고와 설명을 사용한다.
앱 식별자 `com.kjw1801.carelog`는 같은 스토어 앱의 업데이트에서 변경할 수 없다.
바꾸면 별개의 앱으로 취급된다.

## 범위

**V1 필수** — 수유·수면·기저귀, 빠른 기록, 날짜별 기록 목록, 추가·수정·삭제,
SQLite 저장, 오늘 요약, 아이 이름·생년월일, **Android 출시**.

**V1.1 이후** — 일령 표시, 별도 Statistics 화면, 7일 추이 그래프,
백업·가져오기, 수동 다크모드, 수유 타이머, 좌우 자동 추천, 유축, 알림,
여러 아이, 클라우드 동기화.

**V1에 넣지 않는다** — 수유 타이머, 수유 지속시간, 유축, 한 번의 수유에서 좌우
전환, 수유 알림.

**모유·분유 구분과 좌우 위치는 5-5단계에서 V1 범위로 들였다.** 원래는 제외
목록에 있었다. 출시 후에도 기존 기록을 `unspecified`로 보존할 수는 있지만,
미지정 기록이 쌓이기 전에 모델을 확정하는 편이 단순하다.
