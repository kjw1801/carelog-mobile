# carelog — 개발 계획

육아 기록 앱. 수유 / 기저귀 / 수면을 빠르게 기록하고 오늘 요약을 본다.

## 개발 원칙: 기능별 세로 완성

화면을 전부 만든 뒤 DB를 붙이지 않는다. **기능 하나가 Today → SQLite → Records → 수정·삭제까지
전부 동작**하게 만든 뒤 다음 기능으로 넘어간다. 난이도 순서상 수유 → 기저귀 → 수면.

각 단계가 끝나면 변경사항 / 실행 방법 / 확인 항목을 보고하고 멈춘다.
사용자가 직접 실행해 확인한 뒤에만 다음 단계로 진행한다.

## 데이터 규칙

### 수유

| 필드 | 필수 | 비고 |
|---|---|---|
| 수유 시각 | 필수 | |
| 수유 종류 | 필수 | 모유 · 분유 |
| 모유 위치 | 조건부 필수 | 모유일 때만. 왼쪽 · 오른쪽 · 양쪽 |
| 수유량(ml) | 선택 | 분유일 때만. 입력하면 0보다 큰 정수 |
| 메모 | 선택 | |
| 생성·수정 시각 | 내부 | 사용자에게 노출하지 않음 |

**모유는 양이 없고 위치가 있다. 분유는 위치가 없고 양이 선택이다.** 자세한
설계와 마이그레이션은 5-5단계에 있다. `v4 → v5` 마이그레이션된 기존 기록만
`unspecified`로 보존하며, 새 기록은 이 상태로 저장되지 않는다.

**수유량을 입력하지 않으면 `0`이 아니라 `NULL`로 저장한다.**
`0ml`과 `양을 기록하지 않은 수유`는 다른 사실이다.

- 빈 입력 → `NULL`
- 값을 입력하는 경우 → **0보다 큰 정수만** 허용
- `0` 입력 → **입력 오류로 거부한다**

`0ml` 기록을 허용하면 그것이 `마지막 수유` 시각을 갱신해, 이 앱에서 가장 중요한
숫자를 오염시킨다. "물렸지만 먹지 않음"은 수유와 다른 종류의 이벤트이고 V1 밖이다.

집계 표시도 같은 원칙을 따른다. 오늘 분유량이 한 번도 입력되지 않았다면
`총량 0ml`로 보여주지 말고 항목을 숨기거나 `기록 없음`으로 표시한다.
합계는 분유만 더한다 — 모유는 양이 없고 `unspecified`의 양은 종류를 알 수 없다.

### 기저귀

종류(소변·대변·대소변)는 필수다. 자유 문자열로 두면 오타가 조용히 저장되므로
DB 제약으로 세 값만 허용한다.

### 수면

수면은 시각이 아니라 **구간**이다.

- **종료 시각이 비어 있으면 "진행 중"이다.** 수유량 `NULL`과 같은 결로,
  "아직 안 끝남"과 "0분 잤음"은 다른 사실이다.
- **진행 중인 수면은 하나만 허용한다.** 앱에서 검사하고 DB 제약으로도 막는다.
- 종료 시각은 시작 시각보다 뒤여야 한다. 같은 시각도 허용하지 않는다.
- 1분 미만은 `0분`이 아니라 **`1분 미만`**으로 표시한다. 시작과 종료를 연달아
  누르면 실제로 생기는데, `0분`은 기록이 안 된 것처럼 읽힌다.
- 12시간 이상 진행 중이면 종료를 잊었을 가능성을 안내한다. 막거나 자동 종료하지는
  않는다 — 실제로 긴 수면도 있다.
- **겹치는 수면 기록은 저장을 허용하되, 합계에서는 구간을 병합해 중복 시간을
  한 번만 센다.** 낮잠 기록을 나중에 다듬다 보면 겹치는 일이 생기는데, 그때
  저장을 거부하면 더 성가시다. 병합하면 합계가 자연히 조회 구간 안에 들어가므로
  `24시간` 같은 상한을 숫자로 두지 않는다 — 서머타임에서 하루는 23시간이나
  25시간일 수 있다.

### 시각과 날짜 저장

| 값 | 타입 | 이유 |
|---|---|---|
| 수유 시각 (`occurred_at`) | epoch milliseconds `INTEGER` | |
| 수면 시작·종료 | epoch milliseconds `INTEGER` | |
| 생성·수정 시각 | epoch milliseconds `INTEGER` | |
| 아이 생년월일 | `YYYY-MM-DD` `TEXT` | 특정 순간이 아니라 달력상의 날짜다. epoch로 저장하면 시간대가 바뀔 때 날짜가 밀린다 |

SQLite는 ISO 8601 문자열도 정상 지원한다. epoch milliseconds를 고르는 이유는 그것이
옳아서가 아니라, 이 앱이 정렬·범위 검색·두 시각의 차이 계산을 많이 하고
JS와 왕복 변환이 없기 때문이다.

주의: SQLite의 `unixepoch` 계열 함수는 **초 단위**다. 밀리초 값을 그대로 넘기면 안 된다.
날짜 경계는 JavaScript에서 계산하고 숫자 범위로 조회한다.

```sql
WHERE occurred_at >= ? AND occurred_at < ?
```

`occurred_at`에는 인덱스를 건다. 모든 조회가 이 컬럼의 범위 검색이다.

### "오늘"의 경계

**기기 현지 시간 기준 00:00 이상, 다음 날 00:00 미만.**

새벽 수유를 전날 육아 주기에 포함하는 방식도 가능하지만 "하루 시작 시각 설정"이라는
새 기능이 필요해진다. V1에는 과하다.

끝 시각을 `시작 + 86,400,000ms`로 계산하지 않는다. 서머타임 지역에서는 하루가 항상
24시간이 아니다. 현지 달력으로 오늘 자정과 다음 날 자정을 각각 만든 뒤 epoch로 변환한다.
(한국은 서머타임이 없어 실제로 깨지지 않지만, 비용이 없으므로 처음부터 맞게 쓴다.)

### 경과 시간 갱신

"마지막 수유 1시간 24분 전"은 화면을 열어둔 동안 멈춰 있으면 안 된다.

- 화면 표시 중 1분마다 갱신한다
- 백그라운드에서 foreground로 돌아오면 즉시 갱신한다
- 화면을 벗어나면 타이머를 정리한다
- 갱신할 때마다 SQLite를 다시 조회하지 않는다. 마지막 수유 시각만 들고 현재 시각만 갱신한다

### 입력 검증

- **빈 문자열 판정과 숫자 변환을 분리한다.** `Number('')`는 `0`이므로
  `Number(input) || null` 같은 코드는 빈 입력과 진짜 `0` 입력을 둘 다 `null`로 만든다.
- 미래 시각은 저장하지 않는다. 허용하면 "마지막 수유 -5분 전"이 나온다.

### Today 화면 표시 예

```
마지막 수유      1시간 24분 전
오늘 수유        5회
오늘 분유량      220ml
```

## 단계

각 단계는 기능 하나를 Today 입력부터 SQLite 저장, Records 조회, 수정·삭제까지
세로로 완성하고 실기기에서 확인한 뒤 다음으로 넘어갔다.

### 0단계 — 프로젝트 기반 ✅

Expo SDK 57 + TypeScript + Expo Router. 루트 Stack + `(tabs)` 구조로 시작해
모달을 띄울 자리를 미리 확보했다.

### 1단계 — 수유 ✅

SQLite 초기화, 추가·수정·삭제, Today의 마지막 수유와 오늘 횟수, Records 시간순
목록. EAS `development` 프로필로 개발 빌드를 구성했다.

### 2단계 — 기저귀 ✅

수유의 CRUD 구조를 재사용하되 **억지로 범용 프레임워크를 만들지 않았다.**
Records는 통합 타임라인(`src/db/timeline.ts`)에서 두 종류를 시간순으로 합친다.

### 3단계 — 수면 ✅

구간으로 기록한다. **진행 중인 수면은 하나뿐이고 부분 유니크 인덱스로 DB가
강제한다.** 종료는 `ended_at IS NULL` 조건이 붙은 UPDATE라 연타해도 시각이
덮이지 않는다. 앱을 완전히 종료해도 진행 상태가 복구된다.

### 4단계 — Today 요약 ✅

**수면 전체 길이를 더하면 안 된다.** 구간이라 하루에 걸치는 경우가 흔해서 날짜
경계와 겹치는 부분만 센다. 진행 중인 수면의 종료는 `오늘 끝`이 아니라 현재 시각이다.

- **`now`를 인자로 받는 순수 함수로 만든다.** 안에서 `Date.now()`를 부르면 진행 중
  수면 케이스를 테스트로 고정할 수 없다
- **합계는 화면에서 매분 다시 계산한다.** 숫자 하나로 접어두면 진행 중인 수면의
  기여분이 얼어붙는다
- **별도 Statistics 화면은 이 단계에서 만들지 않았다.** 같은 숫자를 다시 배치하는
  것은 값을 하지 않는다. 의미는 7일 추이가 붙을 때 생긴다 — 8단계에서 들였다

### 5단계 — 설정과 마감 ✅

아이 이름·생년월일을 **단일 행 테이블**에 각각의 컬럼으로 뒀다. 타입과 의미가
스키마에 드러난다. 여러 아이 확장과는 무관하다 — 그건 세 기록 테이블 전부에
`baby_id`가 붙어야 하는 별개의 작업이다.

- **일령은 출생일을 `D+0`으로 센다.** 기준은 `daysSinceBirth` 하나에만 두고 경계를
  테스트로 고정했다
- **이름 길이는 글자 수가 아니라 폭으로 센다** (한글 2, 나머지 1, 예산 10).
  제한은 입력할 때와 그릴 때만 걸고 **불러올 때는 자르지 않는다** — 생년월일만
  바꿔 저장해도 이름이 조용히 영구 축약된다
- **헤더는 길이 제한에 기대지 않는다.** 제목을 문자열 하나로 넘기면 뒤에서부터 잘려
  `D+n`이 먼저 사라진다. 두 조각으로 나눠 이름만 `flexShrink: 1`로 줄인다
- **하단 수면 컨트롤은 한 줄이고 위 두 버튼과 높이가 같다.** 상태에 따라 버튼 색
  전체가 바뀐다. 화면을 덮는 오버레이는 쓰지 않는다 — 수면 중에도 다른 기록을
  남길 수 있어야 한다
- **Records는 시각·색 점·종류·값을 한 줄에 둔다.** 세 종류가 같은 형태다. 아이콘
  대신 색 점을 쓴다 — 기저귀에 어울리는 아이콘이 없어 셋을 맞추면 하나는 억지가 된다
- **카드·폼 스타일은 합치지 않는다.** 겹치는 로직은 이미 빠져 있고 남은 것은 스타일
  상수뿐이라, 공통 모듈을 만들어도 각 폼이 다시 덮어쓰고 파일만 하나 는다
- **하루 수면 합계는 `formatDurationCompact`로 버림 표기한다** (`16시간+`).
  반올림한 `약 16시간`은 위로 오해하게 만든다
- **`userInterfaceStyle`을 `"light"`로 고정했다.** 다크 모드를 미룬 동안의 선택이고
  7단계에서 되돌린다

최종 확인은 `preview` 프로필 APK로 했다. `development`는 dev client가 들어가
Metro가 필요해 이 용도에 쓸 수 없다.

### 5-5단계 — 수유 종류 분리 (모유·분유) ✅

**`수유량 NULL`이 두 가지 다른 사실을 뜻하고 있었다** — 모유라 양을 알 수 없는 것과,
분유인데 안 적은 것. 모유가 섞이면 합계가 하루 섭취량 근처도 아닌 숫자가 된다.

`feedings`에 `kind`와 `side`를 더했다(`4 → 5`). 규칙은 [AGENTS.md](../AGENTS.md)와
`src/db/migrations.ts`에 있다. 빈 DB `0 → 5`와 기존 DB `4 → 5`, 기존 컬럼·인덱스
보존과 DB 제약을 검증했다.

- **기존 행은 `unspecified`로 보존한다.** `formula`로 옮기는 것은 추정이다. 양이 있는
  행조차 유축한 모유였을 가능성을 지금 스키마로는 배제할 수 없다
- **새 기록이 `unspecified`가 되는 것은 `CHECK`로 막을 수 없다.** DB는 기존 행 때문에
  그 값을 허용해야 한다. `insertFeeding`의 타입 경계에서 막는다
- **기록 목록의 기존 기록은 양이 있든 없든 `기존 기록`을 먼저 붙인다.** `120ml`만
  보여주면 분유로 오해한다. 추정하지 않으려고 둔 값을 화면에서 감추면 의미가 없다
- **출시 전이 훨씬 쌌다.** 미지정 기록이 쌓이기 전에 모델을 확정하는 편이 단순하다

### 6단계 — Google Play 출시 ✅

2026년 9월 9일 승인. `versionCode 3`, 배포 국가 대한민국.
**표시 이름과 아이콘을 먼저 정했다** — README와 스크린샷을 앞세우면 이름이 바뀔 때
다시 만들게 된다.

- **비공개 테스트 12명·14일은 계정 유형이 아니라 개설 시점에 달려 있다.** 2023년 11월
  이후 만든 개인 계정만 대상이라 해당하지 않았다. **새 계정으로 올린다면 이 순서를
  그대로 쓸 수 없다**
- **Health apps 선언은 `건강 기능 없음`으로 냈다.** 수면 기록이 해당할 가능성이 높다고
  보면서도 내린 선택이다. **8단계에서 `수면 관리`로 바꿨다** — 지적을 기다리지 않고
  고친 이유는 그쪽에 있다
- **처리방침** — 앱 데이터는 기기에 저장되고 개발자 서버로 전송되지 않는다. Android
  자동 백업 가능성을 별도로 알린다. Play 데이터 보안 양식의 `수집` 기준은 기기 밖
  전송이므로 처리방침 문구를 그대로 옮기면 잘못 신고하게 된다. 원문은
  [privacy.html](privacy.html)에 있다
- **자동 백업을 허용한다**(`allowBackup: true`). 앱에 내보내기·동기화 기능이 없어서,
  자동 백업이나 기기 간 전송이 동작하지 않는 환경에서는 기록을 복구할 수 없다. 다만 `true`가 복구를 보장하지
  않으므로 설정 화면도 `기기에만 저장됩니다`가 아니라 `로그인 없이 사용할 수 있습니다`로 쓴다
- **패키지명은 첫 업로드 직전에 바꿨다.** 그 뒤로는 바꿀 수 없고, 바꾸면 기기에서
  별개의 앱이 되어 데이터가 끊긴다. `slug`와 DB 파일명은 내부 식별자라 `carelog` 유지


### 7단계 — 다크 모드 ✅

새벽 수유가 이 앱의 주 사용 시나리오라 어두운 방에서 흰 화면이 그대로 얼굴에 온다.

- `시스템 설정 / 밝게 / 어둡게` 3단. 단순 on/off는 "끄면 무엇이 되는지"가 정의되지 않는다
- `app.json`의 `userInterfaceStyle`을 `"automatic"`으로 되돌린다. 생략하면
  `expo-system-ui`의 기본값이 `light`라 고정과 같다
- 라이트·다크 공통 색상 토큰을 만들고 여섯 화면의 하드코딩된 색을 바꾼다
- 설정은 `expo-sqlite/kv-store`에 저장한다. 육아 기록 스키마를 올리지 않는다
- RN 0.86의 시스템 복귀 값은 `'unspecified'`다. `'auto'`는 이 버전에 없다
- Android 10 이전에는 표준 시스템 다크모드 토글이 없어 "시스템 따름"의 기준이
  기기마다 다르다. 수동 밝게·어둡게를 두는 이유다
- **스플래시는 시스템 테마별 배경을 따로 정의한다.** 수동 앱 테마는 JS가 저장값을
  읽은 뒤 적용되므로 콜드 스타트에서 잠깐 다를 수 있고, 이를 허용한다
- 주요 화면과 날짜·시각 선택기, `Alert`, 스플래시, 상태바·하단 시스템 바를
  네이티브 빌드에서 확인한다
- 한 릴리스에 함께 반영한다. 네이티브 설정은 빌드해야 보이므로 최종 확인용 빌드가
  따로 필요할 수 있다

완료 기준: 세 테마 선택이 저장·복원되고, 주요 화면과 네이티브 UI가 각 테마에서
읽기 편하게 표시된다.

**결과 — preview 빌드에서 확인했다.** 다크 스플래시가 뜨고 크림색 깜빡임이 없다.
시스템이 다크인데 앱을 `밝게`로 두면 날짜·시각 선택기와 `Alert`까지 라이트로 따라온다.
라이트에서 하단 제스처 바가 회색으로 남는 것과 선택기 강조색이 네이티브 기본값인 것은
그대로 둔다 — 둘 다 이번 변경으로 생긴 것이 아니고, 맞추려면 새 의존성이나 네이티브
테마 작업이 붙는다.

### 8단계 — 7일 통계 ✅

기존 데이터로만 만든다. 새 테이블도 입력 화면도 없다.

- 오늘을 포함한 최근 7일을 기기 현지 날짜 경계로 계산한다. `시작 + 86400000`을 쓰지
  않는다 — 서머타임에서 깨진다
- 수유 횟수·분유량·기저귀 횟수·수면 시간을 날짜별 막대로 보여준다
- **횟수의 `0`과 분유량·수면의 `기록 없음`을 구분한다.** Today 화면과 같은 규칙이고,
  `unspecified` 수유량은 분유 합계에서 뺀다
- 수면은 날짜 경계로 자르고 겹치는 구간은 병합한다. 진행 중 수면에는 모든 날짜에
  같은 `now`를 쓴다. `calculateSleepDuration`이 이미 셋 다 한다
- 조회는 기존 함수를 그대로 쓴다. 7일 × 3종이어도 로컬 SQLite에서는 작다. 수면은 7일
  범위를 한 번 조회해 날짜별로 잘라도 된다. SQL 날짜 그룹화는 만들지 않는다
- 차트는 `View`로 만든다. 막대만 두지 않고 날짜와 실제 숫자를 함께 보여준다
- 이름이 `Today`인데 임의 범위를 받는 함수를 일반화한다 —
  `getTodaySummary` → `getFeedingSummary`, `getTodayDiaperCount` → `getDiaperCount`
- 화면은 `오늘 / 기록 / 통계 / 설정`의 네 번째 탭이다
- **Health apps 선언을 `수면 관리`로 바꾼다.** 6단계에서 `건강 기능 없음`으로 낸 것은
  지적받으면 고치기로 미뤄둔 판단이었다. 수면 7일 추이가 붙고 **스토어 설명에 그것을
  직접 광고하게 되면서** 미뤄둘 근거가 사라졌다 — 심사자가 등록정보만 읽어도 수면
  추적이 보인다. 선언은 기능의 분류일 뿐 앱을 의료기기로 만들지 않는다:
  의료기기·진단·치료·의료 조언은 모두 해당 없음, 스토어 카테고리 `출산/육아`와
  데이터 보안 `수집·공유 없음`도 그대로다

평균 수유 간격은 넣지 않는다. 첫 기록 이전 구간을 어떻게 볼지가 정의 문제라 막대
넷과 성격이 다르다.

**결과 — 1.3.0으로 출시했다.** 막대 네 개를 한 화면에 세로로 쌓았다. 2열 배치는
막대가 너무 작았다. 수면은 시간이 아니라 **분**으로 적는다 — 시간 단위는 짧은 낮잠을
`0`이나 `0.1시간`으로 만든다. 진행 중 수면 때문에 `now`를 화면에서 들고 있어야 해서
조회는 접힌 합계가 아니라 **원본 수면 행**을 돌려준다. 접어두면 오늘 막대가 얼어붙는다.
막대 하나가 접근성 노드 하나라 TalkBack이 날짜·지표·값을 한 번에 읽는다.

**스토어 등록정보를 라이브 빌드보다 먼저 바꿔 7일 통계를 광고했다.** 커밋 순서만 보고
출시본을 확인하지 않은 탓이다. 관리형 게시를 켜서 게시를 막고, 1.3.0 AAB·설명·스크린샷·
Health 선언을 같은 검토 배치로 묶어 함께 내보냈다. 재발 방지 규칙은
[docs/store/listing-ko.md](store/listing-ko.md)에 있다.

### 추후 정리

출시 조건은 아니고 저장소 정리다. 사용하지 않는 독립 패키지 `expo-image`,
`expo-device`, `expo-web-browser`와 미참조 템플릿 이미지를 정리한다.
`expo-router`가 요구하는 패키지는 직접 의존성에서 빼도 설치본에 남아 제거 실익이
없으므로 제외한다. 다음 기능 릴리스에 묶어 진행하고 preview에서 회귀를 확인한다.

쓰지 않는 권한은 `android.blockedPermissions`로 이미 막았다.


## 범위

**V1 필수** — 수유·수면·기저귀, 빠른 기록, 날짜별 기록 목록, 추가·수정·삭제,
SQLite 저장, 오늘 요약, 아이 이름·생년월일, **Android 출시**.

**추후 계획** — 더 긴 기간 통계, 평균 수유 간격,
백업·가져오기, 수유 타이머, 좌우 자동 추천, 유축, 알림,
여러 아이, 클라우드 동기화. 다크 모드는 7단계, 7일 통계는 8단계로 들였다.

**알림이나 진동 피드백을 붙일 때 `android.blockedPermissions`를 다시 본다.**
Expo prebuild의 기본 매니페스트는 `SYSTEM_ALERT_WINDOW`, `VIBRATE`,
`READ/WRITE_EXTERNAL_STORAGE`를 "필요 없으면 지우라"는 주석과 함께 선언한다.
V1은 넷 다 차단했다. 차단은 **새로 설치한 모듈이 그 권한을 선언해도 계속
제거한다.** 그래서 알림·진동을 넣으면 기능이 조용히 죽는 게 아니라
`SecurityException`으로 터진다. 그때 목록에서 해당 항목을 빼야 한다.
